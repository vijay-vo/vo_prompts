> New intended difference → add a row in the same edit that creates it.

### ESC-01 · CRC terminal escalation is a registered complaint, not an office visit (2026-07-29)

| | |
|---|---|
| **Axis** | Escalation |
| **CC** | Unchanged. `calltransfer` to the senior team, with the callback flow as the fallback when the transfer fails. |
| **CRC** | The office-visit escalation is **retired**. ### CPL-01 · The complaint block is one canonical protocol in all 18 complaint-capable agents (2026-07-29)

| | |
|---|---|
| **Axis** | Neither — this is **shared truth**. All ten agents per channel that hold `bpcl_create_complaint` carry a block headed `COMPLAINT PROTOCOL — STANDARD`, byte-identical within its channel. |

### CPL-02 · `bookingEligibleAgent` registers its own complaints (2026-07-29)

| | |
|---|---|
| **Axis** | Neither — **shared truth**, implemented identically in both channels. |
| **Before** | `bookingEligibleAgent` held no complaint tool in either channel. A repeated booking failure ended in "here's the distributor's number", and in CRC a complaint could only be reached through `bookingEligibleAgent → routingAgent → genericInfoComplaintAgent` — two silent hops to record a fault the agent had already diagnosed itself. |
| **Now** | It holds `bpcl_create_complaint` and registers **directly**. It never routes anything in order to get a complaint registered; `switchagent` is only ever for a query belonging to another domain. It carries the same `COMPLAINT PROTOCOL — STANDARD` block as every other complaint-capable agent (CPL-01), so both channels now have **ten**. |
| **Complaint-first on a technical failure** | Two or more booking methods failed = a technical fault on our side, not a consumer mistake. Registering the complaint is the **first action**, not a fallback. The distributor's phone number may be offered **only afterwards**, and only if the consumer still wants to book today — a secondary convenience, never a substitute, never offered before the complaint. |
| **Scope** | It registers only within its own scope. **CC:** the technical booking failure, plus recording a callback after a failed `calltransfer` — the same fallback every other CC agent already had, which it could not perform before because it held no tool. **CRC:** the technical booking failure, plus a human/callback request per ESC-01. Anything belonging to another domain is still a `switchagent` route and never a complaint. |
| **CC callback rules, matching the other nine** | Never offered up front and never while a transfer is still possible — only after `calltransfer` fails **and** no complaint has been registered yet in this call. Slot must be 9 AM–5 PM within 15 days; asked twice at most, and if still invalid the complaint is registered anyway without the callback sentence. The callback complaint appends `"Consumer requested a callback on [YYYY-MM-DD] at [HH:MM]."` and **speaks no complaint number** — it confirms the date and time instead. If a complaint already exists (including the technical-failure one), no callback is offered at all. |
| **CC vs CRC** | CC keeps `calltransfer` as its human-request path — a request for a person is a transfer there, not a complaint. CRC has no transfer, so a human or callback request is registered as a complaint per ESC-01. The technical-failure trigger is identical in both. |

### GCD-02 · `getConsumerDetails` carries a MID-CALL ENTRY block in both channels (2026-07-29)

| | |
|---|---|
| **Axis** | Neither — this is **shared truth**, byte-identical in both channels, landed in the same session. |
| **Why** | `getConsumerDetails` is written for entry position ("activated when a consumer is not calling from their registered number") but the platform can activate it **mid-call**, after `Default` has already greeted and triaged. Its only defence was a single clause in the role paragraph — *"You do not greet or introduce yourself"* — and a live CRC call broke it: it opened with "नमस्ते।", added the banned empathy phrase "मैं समझ सकती हूँ", and restated intent the consumer had already given, immediately after `Default`'s "एक मिनट, मैं आपकी delivery details देखती हूँ।" The consumer heard Vaani hand off to herself. |
| **What** | A `MID-CALL ENTRY — YOU ARE NOT THE START OF THIS CALL` section inserted after IDENTITY AND ROLE in both files. Ports the two patterns that already work elsewhere: the leaf agents' continuity block (`postDeliveryAgent.txt:5` — "I am already in the middle of a live phone call … I do not say नमस्ते") and `connectionServicesAgent.txt:11`'s explicit WRONG-first-lines list, including the re-asking-established-intent case. | **Not a fix for the root cause** | The real defect is gate ordering — the data branch resolves *after* `Default` triages, so `getConsumerDetails` runs third instead of first (CRC `agent-workflow.md` §11.3, and DATA-01's note that `Default` runs before the gate). This block contains the symptom; it does not stop `Default` from promising a lookup that is about to become a number request. Platform fix still open. |
| **Verified** | Both blocks hash identically. No channel-specific language in the block — it names no distributor, no office, no team, and no transfer, so it is valid under both Axis 1 and Axis 2 unchanged. |

### GCD-03 · CRC's no-data closing gives the CRC office number; CC offers the senior team (2026-07-30)

| | |
|---|---|
| **Axis** | Escalation |
| **CC** | Unchanged. On the NO-DATA PATH, `getConsumerDetails` **offers the senior team and fires `calltransfer`** on a real consumer confirmation; only if the consumer declines does it fall through to the NO-DATA CLOSING's distributor-referral line (`getConsumerDetails.txt:60`, `:89`, `:117-127`). |
| **CRC** | `calltransfer` does not exist, so the equivalent outcome is a **phone number**. Before this change the consumer was sent to "their distributor" without a name, number, or address, because with no record Vaani holds none of them. The CRC's own office number is static per-office config, not consumer data, so it is available on exactly the path where everything else is missing. |
| **Scope** | All three entries to the closing get it: fetch returned no data (STEP 5), consumer refused twice, consumer has no registered number (STEP 2). Not a complaint and not an ESC-01 escalation — `getConsumerDetails` still holds no `bpcl_create_complaint` and no `switchagent`. |

| **Dictation loop (2026-07-30)** | The number is **dictated, not announced**. Three pieces — 3, 3, 4 digits — one piece per turn, each followed by a single check question ("क्या आपने note कर लिया?" / "जी, note हो गया?" / "आगे बताऊँ?") and a stop. Then the full number is read back **once** for a final confirmation. This is the STEP 2 partial-number behaviour with the roles reversed: there Vaani is noting, here the consumer is. |
| **`callHangup` is gated on the number being noted** | Vaani does not close mid-number. `callHangup` fires only after the consumer confirms the complete number, or on one of exactly three exits: they already have it / don't want it, they cannot write it down at all, or the line is dead across three nudges. Turn count is never a reason to close. The uninjected-variable fallback has no number to dictate and closes immediately. |
| **Uninjected fallback** | Visible curly braces, empty, or a placeholder = no number. Never spoken, never invented — the old distributor-referral line is spoken instead and the call closes as before. |
| **New variable** | `{{crcOfficeNumber}}` — CRC-only, joining `{{crcOfficeCity}}`/`{{crcOfficeAddress}}` (D-05). CC has no physical-office concept, so its absence there is by design, not drift. ⚠️ **Scope superseded by NUM-02 (2026-08-03):** no longer `getConsumerDetails`-only — every live CRC agent except `Default` now holds it, spoken on explicit request only. | **QA prompts** | Both CRC analysis prompts asserted flatly that no senior team exists and that volunteering a phone number is a violation, so they would have flagged the new closing. CC's copies untouched. |
| **Open** | Platform must inject `{{crcOfficeNumber}}` per CRC office; unconfirmed with the platform team at time of writing. Until then every call takes the fallback path, which is the pre-change behaviour. |

Client confirmed the residual gap is under two seconds and, crucially, **the consumer has already been told to wait before it arrives** — which is exactly why the wait cue is last. |
| **What the fixed sentence buys** | It cannot drift into the completed past (CPL-16's entire subject), cannot carry a complaint number (CPL-14/17), cannot have a clause bolted onto it (CPL-08), and **cannot be spoken at all unless the tool is invoked**. Four recurring defects become unrepresentable for that sentence rather than merely forbidden. |
| **The failure mode inverts — the real win** | If the tool does not fire, the consumer hears a restatement and *"एक मिनट रुकिए"*, then nothing. They were asked to wait; **they were never told a complaint exists.** Today that same failure tells them it is registered when it is not. Silence is detectable and alarmable; a false confirmation is not. |
| **Deliberate client decision — registration verbs NOT banned from the agent's own text** | The safest version bans `दर्ज` / `रजिस्टर` / `register` from the agent's own text on that turn, so the promise can only come from the tool. **Client declined** (2026-08-18): the agent may say them, and a restatement using them is not an error. **Known consequence, recorded on purpose:** if the agent does announce the registering in its own text and the tool then fails to fire, the false-promise path is open again for that turn. The design still holds by default — every prompt teaches restatement-then-wait-cue and states that the tool announces the action — but it is a convention now, not a guarantee. |
| **What it does NOT fix** | Modes **C** and **D**. An invented complaint number, or *"register हो गई है"* with no Result, happen **after** the tool returns and are about reading the Result. CPL-15's two-outcome rule and CPL-16's tense gate still own those. |
| **Companion fix — we were teaching the bug** | CPL-11 established by controlled comparison that **code-shaped syntax in the prompt produces narration**. CPL-17 (filed 2026-08-18) then added a detection checklist naming the literal tokens and characters — **putting the demonstration into ten files in order to warn against it.** Reverted. Every such list is now a **whitelist**: *there is exactly one kind of thing you produce — a natural Hindi sentence a person could say out loud; if any part of the draft is written for a machine to read, it is not speech.* CPL-08's older self-check and every surviving `parameter = "value"` form (including `routingAgent`'s two switchagent-retry lines and `connectionServicesAgent` §84) got the same treatment. |
| **Rules reworded to match** | The **TENSE GATE** now says the fixed sentence is in-progress by construction and aims the gate at the agent's own text instead. **REGISTER LINE IS TERMINAL** became **THE WAIT CUE IS TERMINAL** — `"एक मिनट रुकिए।"` is the last thing in the agent's own text, and the only thing that may follow it is the tool's sentence. The tool-turn preambles no longer group the complaint tool with `callHangup`/`calltransfer`: those two speak *only* a `preToolMessage`; the complaint tool carries a fixed one **alongside** the agent's own text — a third case, stated as such. |
| **`promptQA` updated in the same pass** | Left stale it would have flagged correct behaviour and spiked the dashboards. **C3g** rewritten to describe the new two-utterance turn and to state that the pair is correct, not repetition. **C3g-TAIL** re-aimed at the wait cue, since the terminal position moved. **C17** reworded for either registering sentence. Two new checks: **C25** — a *reworded* registering sentence standing where the fixed one belongs means the tool's sentence never played, with an explicit carve-out that Vaani's own restatement may use `दर्ज`/`register` freely; **C26** — a wait cue that leads nowhere is the new signature of a missed call, benign-sounding and therefore easy to miss on a casual listen, reported at C3g severity. |
| **Platform support — CONFIRMED 2026-08-18** | The platform accepts `preToolMessage` on `bpcl_create_complaint` and speaks it while the backend call runs. One QA item stands: confirm it plays **in parallel with** the call rather than after it returns — served late it fills no gap and becomes a post-hoc announcement. |
| **Deliberately NOT changed** | `switchagent` keeps the old contract (own text, no `preToolMessage`) — client scoped this to the complaint tool only, and wants to watch it first. `getConsumerDetails` holds no complaint tool and keeps its two-exception wording. `feedbackDescription` stays an **English summary authored by the agent**, not the consumer's verbatim words — client confirmed. |

The consumer no longer hears the issue summary *inside* the registering sentence; the optional restatement covers it, and the summary the team reads is `feedbackDescription`. |

### CPL-17 · The second registration gets typed out instead of invoked — CRC only, CC pending (2026-08-18)

| | |
|---|---|
| **Axis** | Neither — **shared truth** (§4, *the tool call is the action*). Landed in **CRC only**, in all ten complaint-capable agents. CC carries the same gap. |
| **Source** | Client report, 2026-08-18: happening **in production, on a regular basis**. `postDeliveryAgent` registered one complaint correctly — real tool call, real Result, real number — and then later in the same call emitted: *"आपकी परेशानी को समझते हुए, मैं आपकी शिकायत फिर से दर्ज करने की कोशिश कर रही हूँ, कृपया एक मिनट रुकिए।"* followed by `[bpcl_create_complaint(feedbackDescription="Delivery boy took back the full cylinder…"` — **the call typed out as spoken text**. | **Why the existing rule did not hold** | `OUTPUT-SHAPE SELF-CHECK` (CPL-08) already forbids exactly this and already names the symptom — *"the tool's NAME and then a bracket and parameter text"* — and `postDeliveryAgent` carries it. | **Root cause — the narration is downstream of a forbidden retry** | The give-away is the word **"फिर से"**. The agent was not registering; it was **re-registering**, which `CALL ONCE, NEVER RETRY` and `SAME-ISSUE / DUPLICATE GUARD` both forbid outright. So the turn is a conflict: a consumer pressing for it again, and a rule saying the tool may not be called. **Typing the call out is what that conflict resolves into** — it feels like acting while obeying the ban on acting. It is the one output that both disobeys the rule and fails the consumer. This is why the failure is always **late** in a call and never on the first complaint. |
| **Second driver — the real call is the template** | Once a genuine `bpcl_create_complaint` invocation sits in the context, it is the most available example of "what registering looks like". The new block states this directly: having called the tool successfully already makes the agent **more** likely to type the next one, not less. |
| **Fix — one new standalone block, five parts** | ① The failure named by its real shape and its real timing (*late in the call, after a successful one*). ② Why it happens, with the correct resolution spelled out — **always a sentence, never a typed-out call**: the already-registered line, or the technical-failure line plus the senior-team offer. Both are complete, honest turns that need no tool. ③ The prior-success-as-template trap. ④ **THERE IS NO SUCH THING AS RETRYING A COMPLAINT** — *"फिर से दर्ज कर रही हूँ"*, *"दोबारा try कर रही हूँ"*, *"दर्ज करने की कोशिश कर रही हूँ"* banned as line shapes; **"कोशिश" has no place in a registering line at all**, because on a legitimate registering turn the tool is being invoked, not attempted. The line itself is the warning sign. ⑤ A **literal character check run on every turn**, not only complaint turns: `[`, `(`, `=`, English text in double quotes, and the strings `bpcl_create_complaint` / `switchagent` / `calltransfer` / `callHangup` / `feedbackDescription` / `reason` / `agentName` / `preToolMessage`.
